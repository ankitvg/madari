# ADR 005: Execution Receipt V1

- Status: Accepted
- Date: 2026-07-10

## Context

The bounded Codex run path can describe the launch artifact Madari compiled and
the process result Madari observed. That evidence is useful for local
correlation and review, but it is generated by the same process that performs
the launch. A checksum over that JSON, or a command that merely reparses it,
would not prove host integrity, provider behavior, token scope, or that the
configured controls remained effective outside Madari's observation boundary.

Receipts also sit next to credential-bearing launch state. A generic serializer
over the artifact, command, environment, errors, or output would eventually put
secrets or production data on disk. The receipt contract therefore needs an
independent, deliberately narrow schema and a redaction boundary enforced by
types rather than a best-effort string scrubber.

## Decision

### Opt-in lifecycle

`madari run codex --receipt <path> ...` emits one receipt for an opted-in run.
The path is expanded and made absolute before Codex changes working directory.
Relative paths therefore remain relative to the caller's original directory.
`--receipt` is rejected with `--dry-run` and for non-Codex targets.

When a receipt was requested, Madari attempts the final write for:

- a launch plan that blocks before execution;
- successful client execution;
- preparation, process-start, nonzero-exit, or containment-cleanup failure;
- timeout; and
- handled cancellation.

A receipt-write error is returned to the caller. When execution also failed,
the errors are joined so evidence failure never hides the original run failure.
Madari prints no receipt status line, preserving direct Codex stdout and stderr
passthrough. An uncatchable kill or host crash can prevent a final receipt.

### Independent strict schema

Execution receipts use schema version `1`, independent of the additive command
JSON envelope version used by `--json`. The V1 decoder rejects unknown fields,
unsupported versions, trailing JSON documents, invalid enum values, unsorted or
duplicate evidence arrays, malformed UUIDs and SHA-256 identifiers, and
incoherent outcome/exit/termination combinations.

Every field is present on the wire. Unavailable evidence uses explicit `null`;
collections use arrays, including empty arrays, rather than `null`. The schema
contains:

- a UUID v4 run ID, UTC timestamps, and total duration;
- producer, target, planning/execution phase, outcome, and a bounded reason
  code;
- an explicit `self-reported` evidence label with
  `cryptographic_attestation = false`;
- a nullable artifact object containing required launch and policy digests,
  plus nullable client identity;
- ring, server, and skill names with nullable receipt-safe hashes;
- requested and effective authority records, including `enforced_by`,
  `verification`, and `classification`;
- manifest-declared environment forwarding key names grouped by Codex process,
  stdio server, or remote authentication recipient;
- nullable exact effective timeout in nanoseconds, normalized exit evidence,
  and timeout or cancellation tree-termination evidence.

Hashes use the `sha256:<64 lowercase hex>` form. They correlate the receipt with
receipt-safe configuration evidence; they are not signatures or host/provider
attestation.

### Redaction by construction

The receipt finalizer accepts only sanitized names, enums, timestamps, counters,
and receipt-safe digests. It does not accept the prompt, artifact body, command
line, environment values, auth paths or bytes, output streams, temporary paths,
process IDs, or raw errors.

V1 never serializes:

- prompt text or a prompt hash;
- command or argument values;
- URLs, header names or values, or credential values;
- environment values;
- Codex authentication content or paths;
- skill bodies;
- stdout or stderr; or
- raw error messages.

Environment variable *names* are intentional evidence. They show which
manifest-declared values Madari configured for each recipient without revealing
the values. They do not claim that a recipient started or observed the value.
The documented platform baseline and generated isolated-path values are part of
the bounded execution contract, not the declared-forwarding list.

### Private atomic write

Receipts are serialized deterministically with a trailing newline and written
through Madari's atomic file helper using owner-only mode `0600`. On Windows the
same helper applies a protected current-user DACL. Replacement keeps the final
receipt private rather than inheriting a permissive mode from an old file.

## Consequences

- A reviewer can correlate a run with immutable, receipt-safe configuration and
  bounded process observations without storing credentials or model output.
- Planning blocks and execution failures still produce bounded evidence when
  the requested destination is writable.
- Receipt V1 can evolve independently from normal CLI JSON.
- A receipt proves only what Madari says it configured and observed. Behavioral
  or provider verification requires an independent future boundary.
- Madari does not add a `verify` command that merely checks its own JSON or a
  self-generated checksum.
